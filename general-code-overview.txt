-) Introduction
=====================================================================

   The code of QPV is poorly structured and organized. It relies on
   many global variables... and is hard to follow. This is the result
   of me having no prior experience in coding such large projects.
   It is a miracle it all works... ^_^ I should have used classes 
   to define objects such as «file list», «indexed item», «viewport
   image», et cetera, and have constructors for the different kinds of
   tools. This document is meant to help people get their mittens into
   the code of Quick Picto Viewer by offering pointers to the main
   functions and how things connect / work.

   Another big problem of the project is the reliance on GDI+. This 
   hinders the performance of the application. I should have used 
   Direct2D and shaders. In addition to this, I find it likely there
   are better image libraries than FreeImage, eg. OpenCV perhaps.

   And finally, AHK v1.1 is fundamentally not a wise choice for
   coding such a big application, even had I used classes 
   to better structure the code. AHK's loops are utterly slow, 
   rendering any processing of large amounts of data... a pain.
   I circumvented this by creating my own DLL in C++ which I rely 
   on to process data.

   In 2024, QPV v6.0 was a major development push. This version brought
   full support for images above 536 megapixels (the limit of GDI+),
   through FreeImage. Most of the image editing tools work with such
   images - through my own DLL: qpvmain.dll. In 2026, another major
   development drive was possible with AI. Using Gemini and Claude,
   I optimized and overhauled various parts of QPV. Multi-threaded 
   thumbnail generation and image duplicates detection were
   reimplemented in C++. Many image editing tools are now much
   more efficient.

   I use a custom build of the FreeImage.DLL. Because the developer 
   behind FreeImage rarely updates the library, I decided to make my 
   own version. It has multiple fixes and improvements. It can be 
   found on GitHub:
   https://github.com/marius-sucan/FreeImage-library/tree/qpv

   In v6.3.5, I eliminated AutoHotkey_H [AHK_H]; see section p).


a) How Quick Picto Viewer initializes
=====================================================================

  If QPV is started with the command line argument qpv-core-thread=N,
  it runs as a worker for multi-core batch processing: the main
  instance starts one such QPV process for each core in use, through
  launchExternalCoreThread(). initExternalCoreMode() reads the job
  from the registry and the list of files from a text file, processes
  the files and exits, without going through the steps below.

  QPV checks in the registry whether another instance started before;
  if it did less than 600 milliseconds ago, it exits. This is meant
  to prevent a profusion of instances.

  It then loads settings or stores default settings [on first start].
   - readMainSettingsApp() or writeMainSettingsApp(). These two functions
  load and write only the core settings in an INI: quick-picto-viewer.ini.
  Each panel [or tool] within QPV loads and stores settings that
  pertain only to it, in the registry. Such functions are
  named using this pattern: "ReadSettings*Panel".

  initInterfaceModule() registers the input handlers and BuildGUI()
  creates the main window and the viewport windows. If BuildGUI()
  fails, QPV shows an error and exits. createGDIPcanvas() and
  InitGDIpStuff() then create the GDI+ canvases and the GDI+ objects
  related to them.

  initializeAppWithGivenArguments() processes all the arguments
  given on the command line. The user can set global variables using
  set_GlobalVar and invoke functions that take no parameters with
  call_funcName(). Examples:

      qpv.exe "fd=C:\example folder\tempus"
      Add a pipe "|" after equal "=" to have images loaded non-recursively.

      qpv.exe call_ToggleThumbsMode() "fd=C:\folder\tempus"

      qpv.exe set_IMGresizingMode=3 set_vpIMGrotation=45 "C:\folder\this-image.png"
  
  If an image file is given as a command line argument, it is
  opened with OpenArgFile(). If a .SLD or a .SLDB file is fed,
  OpenSLD() is used to load the files index. Folders 
  are opened using OpenFolders().

  If no argument is given, it draws a random pattern image using
  drawWelcomeImg(). This function can generate up to 10 distinct
  patterns, each randomized in its own way.

  In the 32-bit edition, the following settings are in effect by default:
     allowMultiCoreMode := 0
     minimizeMemUsage := 1
     maxUndoLevels := 2
     These are meant to limit memory usage as much as possible.

     Side note: the 32-bit edition is no longer actively tested.


b) How a files list index is created
=====================================================================

  If a single file is loaded, QPV internally sets the variable
  "mustOpenStartFolder" to the path of the image's folder.

  If the aforementioned variable is set, various user actions will
  trigger the indexation of the files found in the folder using
  doOpenStartFolder(). Examples of such actions: toggle thumbnails
  mode, search, attempt to go to the next or previous image, and so on.

  Once the folder is indexed, "mustOpenStartFolder" is emptied.

  Users can open a folder using the open file/folder dialogs:
  OpenDialogFiles() or OpenFolders(). Both functions, and 
  doOpenStartFolder(), rely internally on coreOpenFolder().

  coreOpenFolder() takes as argument the folder to index files
  from. If the folder string contains a pipe "|", the files will
  not be indexed recursively. The function renews / clears 
  the previous files list with renewCurrentFilesList() and then
  it proceeds to scan for the files using GetFilesList().

  In essence, coreOpenFolder() is a wrapper for GetFilesList(),
  which uses a regular expression held in "RegExFilesPattern"
  to match supported file types.

  QPV internally relies on the resultedFilesList[] array object. 
  Each file entry is defined by various properties:

  The resultedFilesList[] array object is populated by GetFilesList(),
  OpenSLD(), sldGenerateFilesList(), OpenSLDBdataBase(),
  performSQLgetTable(), dbSortingCached(), SortFilesList() and others.

  resultedFilesList[index_number] :=
  [ 1_filePath, 2_isSelected, 3_isSeen, 4_forceThumbRefresh
  , 5_isFavourite, 6_fileSize, 7_fileDateModified
  , 8_fileDateCreated, 9_imgFrames, 10_mustDoSort, 11_IsImgHisto
  , 12_dbRowIndex, 13_imgW, 14_imgH, 15_imgPixFmt, 16_imgWHratio
  , 17_imgMGPX, 18_imgHAvg, 19_imgHmedian, 20_imgHpeak, 21_imgHlow
  , 22_imgDPI, 23_dupeID, 24_imghStdDev, 25_imghRange, 26_imghMode
  , 27_imghMin, 28_unused, 29_unused, 30_unused, 31_unused
  , 32_unused, 33_HammingDist, 34_MSEscore, 35_dateSeenDB
  , 36_sortModeDB]

  29 to 32 used to hold the four pixel fingerprints. They are BLOBs in the
  imagesPixels table since SLDB schema v3 and are produced, read and compared
  entirely inside qpvmain.dll; nothing in AHK ever holds one. The slots are
  left numbered rather than reused so that every other index keeps its meaning.
  28 used to hold the image hash in use for Hamming distance.

  All these properties are optional and are filled based on the
  application context. 1_filePath is the only property that is not
  optional, because it specifies the file path and image file at
  the given index entry.

  When [de]selecting a file, resultedFilesList[Index_number, 2]
  is set to 1 or 0.

  If "skipSeenImagesSlider" is set to 1, when an image is displayed
  resultedFilesList[Index_number, 3] is set to 1. By default,
  this feature is not enabled.

  When GetFilesList() and coreOpenFolder() finish, in most cases,
  a random image is chosen to be opened. However, when a file is
  already loaded, detectFileID(imgPath) is used to identify and
  set the initial file index to the image already loaded.

  If a slideshow database is already open, GetFilesList() will
  automatically add the files into the database using addSQLdbEntry().
  In this context, the file names are converted to lower case.

  The properties holding file details are optional, as previously indicated.
  They are filled by GetFilesList() or collectFileInfosNow() and are used
  as caches by SortFilesList(), the files statistics panel and
  QPV_listThumbnailsGridMode(). The collectImageInfosNow() function fills
  the members of the object with details about images and their main 
  histogram points. These details, once cached, are used for sorting files,
  by the file statistics panel and for finding image duplicates.

  GenerateRandyList() is called to generate a randomized array
  of file index numbers from 1 to "maxFilesIndex", non-repetitive.
  RandyIMGids[] array is used whenever the user navigates randomly
  through the indexed files.

  The current position within the index list is held by
  "currentFileIndex" and the number of indexed files in "maxFilesIndex".
  The current «random» position is "RandyIMGnow".

  Internally, "CurrentSLD" holds what folder or slideshow file 
  the user has opened, while "SLDtypeLoaded" indicates the type:
    1 - folder
    2 - slideshow plain-text
    3 - SQLite slideshow database

  If the user opens a slideshow file [a cached index], OpenSLD()
  is invoked. This is a wrapper for sldGenerateFilesList() and
  OpenSLDBdataBase().

  sldGenerateFilesList() parses plain-text files. Their INI-like
  saved settings are loaded by INIreadSlideSettings().

  OpenSLDBdataBase() opens SQLite3 databases and reads the
  settings using readSlideSettingsInDB() and IniSLDBreadGiven().


c) Files index filtering
=====================================================================

   Users can apply a filter on the indexed file list through
   PanelEnableFilesFilter(). It can be a RegEx or a string
   that allows "|" to act as the OR operator.

   coreSetFilesFilteru() processes the string given by the user in 
   "usrFilesFilteru". The internal filter is held in "filesFilter".

   FilterFilesListuIndex() is the core function that generates the
   filtered new list. A backup of the main list is created:
     bckpResultedFilesList := resultedFilesList.Clone()
     bkcpMaxFilesIndex := maxFilesIndex

   A map of the indexes between the two arrays is created:
   filteredMap2mainList[Index_number] := Index_number_main_list

   filteredMap2mainList[] array is used when the user performs
   actions that change the index and have to be propagated in 
   the main list [the backup]. For example: file rename, index
   entry removal and so on.

   When the new resultedFilesList[] array is created, all entry 
   properties are maintained.

   FilterFilesListuIndex() can take Regular Expressions or «queries».
   Strings that begin with: «SQL::query::» will be parsed and used
   to perform a SELECT in the currently loaded SQL database. For
   example: SQL::query::WHERE fmodified LIKE '20200607%' .

   If the user does not work with an SQL database, another type
   of query can be used to filter the files list: «QPV::query::»
   These are structured as follows:
   QPV::query::what::minRange::maxRange::optionalString

   Example: QPV::query::fsize::100002::250001::string

   When such queries are performed, Quick Picto Viewer uses cached
   data when available, otherwise it will extract image or file
   details. The collected data is cached in memory for subsequent
   queries or index sort operations. If an SQL database is open, 
   the data will be stored in the database as well.
   
   The function FilterFilesListuIndex() ends by invoking
   GenerateRandyList().


d) How an image is loaded and displayed on screen
=====================================================================

   To display an image, one can invoke IDshowImage(given_file_index)
   or ShowTheImage(imgPath).

   IDshowImage() retrieves the image file path based on a given
   number from resultedFilesList[] array and can filter dead
   files, if "skipDeadFiles" is set to 1. It can also reset
   viewport viewing conditions if "resetImageViewOnChange" is
   set to 1.

   ShowTheImage() is called with the full file path by IDshowImage().
   This function is a wrapper for coreShowTheImage() to let the user 
   quickly skim through indexed files without loading and displaying
   each of them. It takes into account how fast the user changes
   between images and how fast they are rendered on screen. If the 
   system resources permit this, all images will be displayed. However,
   if load times are high, then many images will be skipped. To this
   end, there are various timers meant to slightly delay image loading, 
   to allow for interruptions.

   IDshowImage(), ShowTheImage() and coreShowTheImage() are invoked
   even if the user is in list mode [thumbnails view].

   coreShowTheImage() ends abruptly by setting the window title
   and invoking UpdateThumbsScreen() if the user is in thumbnails
   mode. Otherwise, it continues by invoking ResizeImageGDIwin().

   coreShowTheImage() also checks for file existence and can show
   error messages to users.

   ResizeImageGDIwin() and coreShowTheImage() keep track of the 
   currently loaded image file and previous one, to help decide 
   if cached GDI bitmaps must be used or not. They can discard
   all cached image data.

   Images are cached as GDI+ bitmap objects by Quick Picto Viewer.
   This occurs at different levels or stages. This enables users
   to delete an image file, go to the next one and, if they choose,
   return to the deleted one and find the cached image, and resave it.

   If no cached GDI bitmaps are available or a different image
   file is loaded, ResizeImageGDIwin() will call CloneScreenMainBMP().

   CloneScreenMainBMP() manages «original» image caching and
   pre-processes images for display: rotate, convert depth modes. It
   caches only two images at a time. This function can abort image
   processing if the user attempts to change the image before it
   finishes. It sets "canCancelImageLoad" to 1 and checks it between
   its steps; the input handlers of the viewport set it to 4, which
   means abort, eg. when the user clicks the viewport or presses a
   navigation key.

   CloneScreenMainBMP() is called only by ResizeImageGDIwin().
   coreShowTheImage() is the only function that can invoke
   ResizeImageGDIwin().

   LoadBitmapForScreen() is called by CloneScreenMainBMP(). This is
   the function that accesses files. It is a wrapper for three
   functions that return a GDI+ bitmap:
      - LoadWICscreenImage()- loads images through Windows Imaging Component;
                              it has been the preferred loader since v5.6.0
      - LoadFimFile()       - used to load additional file formats
                            - this function converts any image to a 24 or
                              32 bits depth and then to a GDI+ bitmap object
      - LoadFileWithGDIp()  - loads GDI+ supported files
      - LoadFileWithWIA()   - the fallback function of LoadFileWithGDIp()
                              for very large images
                            - WIA stands for Windows Image Acquisition

   LoadWICscreenImage() calls DLL functions found in qpvmain.dll: 
   WICpreLoadImage(), WICgetRectImage() and WICdestroyPreloadedImage().
   WICpreLoadImage() returns the handle and properties of the image to
   be loaded. WICgetRectImage() returns a GDI+ bitmap object. It is
   invoked only if the image does not exceed the GDI+ limit of 536 mgpx.
   When the image exceeds 536 megapixels, it is transferred to FreeImage
   using teleportWICtoFIM().

   LoadWICscreenImage() and LoadFimFile() can return to LoadBitmapForScreen()
   the string "very-large", when an image over 536 megapixels was loaded.
   In this context, the image is a FreeImage object and the "gdiBitmap"
   GDI+ bitmap is just a dummy. The object is "viewportQPVimage" and it is 
   created via the "screenQPVimage" class.

   LoadBitmapForScreen() returns a GDI+ bitmap handle on success.
   CloneScreenMainBMP() passes "allowCaching" as 1, unless
   "minimizeMemUsage" is set or an image is being edited, which
   allows this function to cache the previously opened file,
   unprocessed by CloneScreenMainBMP().
   It also fills in the properties of currIMGdetails[], which
   holds various details of the image about to be displayed.

   When CloneScreenMainBMP() finishes loading and processing the image,
   in ResizeImageGDIwin() the GDI+ bitmap dimensions and user 
   viewing options are used to calculate the dimensions of the image
   in the viewport and the selection area, if present.

   QPV_ShowImgonGui() is then invoked with multiple parameters.
   This is the function that will render the image on screen.
   On every frame, the visible part of the image is resized to its
   size in the viewport by OpenCV_GdipResizeBitmap(), which calls
   openCVresizeGdipBitmap() found in qpvmain.dll. The DLL function
   locks the GDI+ bitmap in its own pixel format, resizes the given
   rect with OpenCV and returns a new 32-PARGB bitmap, which is
   then drawn by GDI+. If no bitmap is returned, Gdip_DrawImage()
   scales the image for that frame.

   High-quality frames use the area interpolation when the image is
   shown smaller than it is, and the cubic one when it is enlarged.
   Low-quality frames use nearest neighbour. These are drawn while
   the user pans or zooms, when "userImgQuality" is set to 0, when
   an image editing tool is active and at zoom levels above 1000%.
   A high-quality frame follows a low-quality one after a delay,
   unless the view itself calls for low quality.

   QPV_ShowImgonGui() can also generate reduced copies of the image.
     - "gdiBMPvPsize"   - handle of a viewport sized image
     - "gdiBitmapSmall" - handle of a low-res sized image;
     - the dimensions are calculated in determineGDIsmallCacheSize()

   These are obtained by resizing "gdiBitmap", the bitmap returned 
   by CloneScreenMainBMP(), but only if "userImgQuality" is set to 1.
   A copy is made when the image changes its size on screen, and
   it is used only while the image is shown at the size of the copy
   or smaller.

   The frame rendered, without colour effects and without flips, is
   held in the variable named "ViewPortBMPcache". It is drawn again
   for as long as the image, its position and its size on screen are
   the same. The colour effects and the flips are applied on it.

   If the image loaded exceeds 536 megapixels, the reduced copies
   are not created: gdiBMPvPsize, gdiBitmapSmall. QPV_ShowImgonGui()
   calls retrieveQPVscreenImgSection() instead. This function renders
   and displays very large images. Internally, it caches a
   viewport-sized image.

   decideGDIPimageFX() is used to obtain GDI+ objects that can alter 
   the display of colours: a colour matrix and an Effects object.

   drawHUDelements() is the function that renders the scroll bars, 
   current frame index (visual indicator), the grid ( drawVPgridsNow() )
   and the histogram box ( createHistogramBMP() ) on the viewport.
   These UI elements are rendered on a different GDI window.
   drawHUDelements() also invokes additionalHUDelements(), a function
   that wraps additional HUD elements: drawImgSelectionOnWindow(),
   drawAnnotationBox(), VPnavBoxWrapper(), and drawinfoBox().
   additionalHUDelements() is often invoked in the code to update the
   selection area and/or other HUD elements.

   QPV_ShowImgonGui() tracks how fast the rendering on screen is and
   adaptively chooses between low- and high-quality frames.

   Internally, QPV uses the 32-ARGB pixel format: the DLL functions
   lock the bitmaps in it, so GDI+ converts nothing on a lock. The
   thumbnails made by the DLL workers and the bitmaps returned by
   OpenCV_GdipResizeBitmap() are 32-PARGB; they are only drawn.
   An image held in another format is converted when an edit begins,
   by editedImageToCoreFormat(): UserMemBMP is always 32-ARGB.

   There are four EX_LAYERED windows: "hGDIthumbsWin", "hGDIwin",
   "hGDIselectWin", "hGDIinfosWin". There are two global GDI+
   Graphics, with their own HDCs and GDI hBitmaps: glPG / glHDC
   and 2NDglPG / 2NDHDC. These are recreated upon window resize
   events. These windows are created by BuildGUI() found in
   "module-interface.ahk". The GDI+ canvases are created by
   createGDIPcanvas() found in the main QPV.ahk file. Auxiliary
   GDI+ objects are created in initGDIPstuff().

   See section g) for more details on what windows are created.


e) General considerations
=====================================================================

   When actions are performed or somehow QPV is about to get
   busy, changeMcursor() and/or setImageLoading() are called.
   They switch the mouse cursor to the busy one through
   uiChangeMcursor(); setImageLoading() also sets "imageLoading".
   When the work is done, ResetImgLoadStatus(), often run from a
   timer, restores the normal cursor and clears the busy flags.

   For operations that can be aborted, doStartLongOpDance()
   is called. It sets "imageLoading" and "runningLongOperation"
   and calls initAppBusyMode(), which clears the abort flags,
   starts the busy progress animation of the taskbar button and
   disables the menu bar.

   The loops of such operations regularly call
   determineTerminateOperation() to see whether the user's
   intentions changed, to abort the current operation[s] or
   continue. It returns "mustAbandonCurrentOperations", which
   askAboutStoppingOperations() sets when the user answers «Yes»
   to its prompt. The prompt opens when the user clicks the
   viewport, presses Escape or tries to close the window while the
   operation runs. This works because AHK checks for window
   messages at short intervals and launches the input handlers
   even while a loop holds Critical; timers wait until the
   operation ends.

   QPV_post() queues a function call: the function runs a moment
   later, from a one-shot timer, never inline. The input handlers
   use it to hand work over, eg. MouseMoveResponder(), and the
   drawing functions use it to update the screen-reader controls,
   uiAccess*().

   For more details about the interface, please see section g).

   Many GDI+ functions are wrapped to keep track of the bitmaps 
   created and to avoid memory leaks. These are prefixed with 
   "trGdip_*".


f) How slideshows happen
=====================================================================

   When the user starts a slideshow, InformToggledSlideShowu() is
   called. It opens the pending start folder, if any, and calls
   ToggleSlideShowu(), which toggles the slideshow and gives the
   user information about it.

   The whole slideshow «business» is convoluted. The purpose 
   was to obtain an easy-to-stop slideshow in any circumstance,
   even if it is running very fast or the user loads very large 
   images and applies all the possible real-time effects.

   To this end, the slides are driven by a one-shot timer that runs
   theSlideShowCore(). ToggleSlideShowu() sets it on start. When it
   runs, theSlideShowCore() calls one of these functions:
   RandomPicture(), PreviousPicture() or NextPicture() - based on
   user preference. When the new image is displayed,
   scheduleNextSlide() sets the timer again, so the delay of each
   slide counts from the moment its image is on screen.

   The input handlers stop the slideshow at once, through
   stopGifORslidesPlayback(), when the user clicks the viewport or
   presses a key such as Escape or an arrow key. theSlideShowCore()
   also stops it when such a key was pressed since the last slide
   [ProcessCriticalKeys() keeps the last key]. stopSlideshow() is
   the function that ends a slideshow.

   "SlideHowMode" is the variable designating the slideshow mode
   and "slideShowDelay" is the delay chosen by the user, in
   milliseconds. The timer uses "slideShowCadence", set on start:
   the same delay, or the length of the audio file associated with
   the image, when that is longer. "slideShowRunning" is a boolean.

   Things get even uglier with GIF animations...
   autoChangeDesiredFrame() is used for animated GIFs and it is 
   run with the first parameter set to "start" only from 
   QPV_ShowImgonGui() and restartGIFplayback(). It is also invoked as a timer.

   Because I wanted users to have the option to allow GIFs to 
   play entirely before going to the next slide,
   autoChangeDesiredFrame() sets "allowNextSlide" to 0 while the
   GIF plays, and theSlideShowCore() does nothing while it is 0.
   When the first loop is done, it is set to 1 and, once the slide
   delay has passed, autoChangeDesiredFrame() sets
   theSlideShowCore() to run at once.


g) Windows, AHK GUIs, Menus, Toolbar
=====================================================================

   "module-interface.ahk" holds the main window, the viewport
   windows, the menu bar and the input handlers of the main window
   and of the viewport. The processing and the drawing happen in
   the main file, "quick-picto-viewer.ahk", and in qpvmain.dll.

   The following is a list, a summary, of which functions draw
   what and on which window(s).
   All the windows are owned by the "PVhwnd" window.
   These are created by BuildGUI(), found in "module-interface.ahk".

   0. PVhwnd - the variable holding the handle of the main window of QPV
      where various text controls are added

   1. hGDIthumbsWin - glPG         - layered window
      QPV_listThumbnailsGridMode() - thumbnails grid for the list mode
      QPV_ShowThumbnails()         - draws and generates thumbnails
      
      During live image editing
         QPV_ShowImgonGui() - image on screen
         drawHUDelements()  - histogram box [image view only]
                              various UI markers [frames counter, scrollbars]

   2. hGDIwin - glPG             - layered window
      livePreviewsImageEditing() - the live image editing tools
         corePasteInPlaceActNow()
         coreDrawLinesStuffTool()
         coreFillSelectedArea()
         livePreviewInsertTextinArea()
         livePreviewEraseArea()
         livePreviewDesaturateArea()
         ... and others

      When NOT in live image editing
         QPV_ShowImgonGui() - image on screen
         drawVPgridsNow()   - viewport grid
         drawHUDelements()  - histogram box [image view only]
                              various UI markers [frames counter, scrollbars]

   3. hGDIselectWin - 2NDglPG - layered window
      QPV_ListViewGridHUDoverlay() - thumbnails grid overlay, scrollbar and status bar
      additionalHUDelements()      - wrapper for the following functions
         drawImgSelectionOnWindow() - selection area [image view only]
         drawinfoBox()              - infos box
         VPnavBoxWrapper()          - image navigation/preview box
         drawAnnotationBox()        - image captions box [image view only]
         drawLiveCreateCustomShape() - live shape drawing [image view only]

   4. hGDIinfosWin - 2NDglPG - layered window
      CreateOSDinfoLine()    - user OSD messages
      MouseMoveResponder()   - hover selection area handler

   5. ShowClickHalo() - MclickH; on-demand, temporary window. It
   briefly highlights the active control of a panel, when
   highlightActiveCtrl() requests it.

   6. mouseCreateOSDinfoLine() - mouseToolTipGuia; on-demand,
   temporary window. It displays messages for the user, where 
   the mouse is located.

   If any of the aforementioned windows, from 0 to 4, fails to be
   created, Quick Picto Viewer shows an error and exits.

   QPV creates the following AHK windows on demand:

   1. PanelFoldersTree() - folders tree navigation and manager
      hfdTreeWinGui, fdTreeGuia

   2. PanelQuickSearchMenuOptions() - searchable menu options
      hquickMenuSearchWin, QuickMenuSearchGUIA

      It can also function as a folders manager and navigation tool,
      if a folder path is provided, instead of keywords.

   3. createSettingsGUI() - a generalized panel used by most
   of the panels users can see in QPV. Each panel has an ID,
   assigned to the "AnyWindowOpen" variable.
      hSetWinGui, SettingsGUIA

      It must be noted that some panels are constructed by 
      fakeWinCreator() which uses msgBoxWrapper() to create
      simple panels.

      repositionWindowCenter() is called after any panel is created. 
      This function repositions the window in the centre of the
      screen where the main QPV window is. It also applies the dark
      mode theme to all its controls.

   4. msgBoxWrapper() - custom message boxes of all kinds
      MsgBox2hwnd, WinMsgBox

   5. createGUItoolbar() - customizable toolbar
      hQPVtoolbar, OSDguiToolbar
      redrawToolbarGUI() - active or inactive toolbar states

   6. CreateSoloSliderWidgetWin() - a sliders widget
      hSliderWidget, SoloSliderWidgetGUIA
      It is used as a popup for some tools found in the
      toolbar.

   7. CreateCollapsedPanelWidget() - collapsed panel widget
      hCollapseWidget, collapseWidgetGUIA
      It is invokable by collapsing the panel of a live tool.


   QPV shows messages in the viewport using CreateOSDinfoLine(),
   wrapped by showTOOLtip().

   The main GUI of the QPV window, created in BuildGUI(),
   contains multiple static text controls. These are used
   as placeholders. They are updated with texts pertaining
   to the various viewport elements. The functions that
   update the controls are uiAccess*(). drawHUDelements() and
   other associated functions invoke them, mostly queued with
   QPV_post(). This is meant to help make the viewport more
   accessible for users relying on screen readers.

   adjustCanvas2Toolbar() is used to decide if the viewport gets
   shifted when the toolbar is attached to the main window.


   \\Contexts:
   Toolbar and menu related functions decide what options to display
   based on the app/user context and user settings. Broadly speaking,
   there are several modes and their associated global variables:
     - thumbnails list view
       var: thumbsDisplaying = 1

     - image view
       var: thumbsDisplaying = 0
       - live image editing tools
         var: imgEditPanelOpened = 1, AnyWindowOpen > 0

         - alpha masking brush mode (sub-mode of live image editing, never otherwise)
           Detectable via: isNowAlphaPainting()

       - freeform vector shapes editor (sub-mode of image view, never otherwise)
         var: drawingShapeNow = 1

   These contexts apply to the keyboard shortcuts as well.


   \\The custom controls:
   In the panels created with createSettingsGUI(), many controls,
   even if not actually customized, are wrapped just for the
   sake of improving accessibility for screen readers and to add
   tooltips easily, eg. GuiAddEdit().

   The custom sliders are created with GuiAddSlider() and respond to
   user input via GuiSlidersResponder(). When created, they are
   usually set to invoke the panel's specific UI function prefixed
   with "updateUI*".


   \\The menus:
   The context menus are created via InitGuiContextMenu(),
   invokeTlbrContextMenu() and others. The menus are displayed with
   showThisMenu(). The menu bar is created by BuildMenuBar() and
   uiKmenu(), found in "module-interface.ahk". Each item of the bar
   has its menu attached as a submenu, and the functions that build
   these menus are in the main file: their names begin with
   "InvokeMenuBar*". Just before a menu of the bar is displayed,
   uiMenuBarJITrebuild() calls its InvokeMenuBar*() function, which
   rebuilds the menu in place [uiInstallSentMsgHook() installs the
   hook that catches WM_INITMENUPOPUP for it]. Called with
   "justBuild" set to 0, the same functions display their menu with
   showThisMenu(), eg. for the buttons created by CreateTempGuiButton().
   Why did I do it like this? I hate
   when apps display all kinds of pointless options that are not
   relevant to the current context, e.g., the Text menu in Affinity Photo
   when no text object is manipulated. It is all clutter. As such,
   I find it imperative to generate the list of menus and sub-menus
   dynamically, to only display what is relevant. For the same
   reason, BuildMenuBar() picks the menus of the bar based on the
   app mode.

   All the menus, and the context menus, are created with the standard 
   Menu command of AHK; however, I created a wrapper function for it.
   The list of menus is generated on the go, on demand, based on 
   app/user context[s]. The wrapper helps keep track of the menus
   generated: kMenu(). It records menu names, states and keywords.
      objuA - menu items by index with properties objuA[menuIndex] := [prop1, prop2,... etc]
      objuB - maps menu-name and menu-item pairs to indexes of objuA; objuB[menu "-" label] := menuIndex
      objuC - menu-names and their properties objuC[menu] := [menu-name, container-menu, accelerator-key]

   The menus are searchable via PanelQuickSearchMenuOptions() -->
   uiPopulateQuickMenuSearch() --> buildQuickSearchMenus(). The global
   variable "mustPreventMenus" is set to 1 before generating the
   searchable list of the menus. When this is used, some menu items
   are hidden, while others are added, and the menus themselves are
   not invoked. When this variable is set to 1, showThisMenu() does
   not display the menu on screen.


   \\The toolbar:
   The GUI of the toolbar is created by CoreGUItoolbar().
   createGUItoolbar() is a wrapper that filters the calls to the 
   main function, to minimize them, and loads the toolbar settings.

   CoreGUItoolbar() holds the list of possible toolbar icons and 
   their properties in the form of:
     localStaticBtnID := [ico-file-name, 0, base-user-friendly-name, 0, button-ID, 0, menu-mode, modes-availability]

   Buttons in the toolbar are added via tlbrAddNewIcon(). The list 
   of those added is held in this object: "tlbrIconzList".
     tlbrIconzList[btnID/hwnd/index] := [ctrl-hwnd, icoFile, btnName, btnType, indexBtn, function-to-call, icoW, icoH, param-func, btnID, menuMode]

   The buttons are typical AHK / Win32 button controls customized 
   using the ImageButton class. It is a class that assigns ImageLists
   to push buttons using the ImageList_Create Win32 API function.

   The toolbar can be customized by users via PanelCustomizeToolbar().
   The custom toolbar is loaded only if userCustomizedToolbar equals 1.
   "userThumbsToolbarList" and "userImgViewToolbarList" hold the lists
   of the user's customized toolbars for the thumbnails list and the image view.
   The other modes cannot be customized.

   WM_MOUSEMOVE(), the mouse-move handler of the panels and of the
   toolbar, invokes tlbrDecideTooltips() to dynamically display
   tooltips for the toolbar buttons, which can change based on
   the context.

   The toolbar buttons' actions are invoked via tlbrInvokeFunction() -
   a wrapper that utilizes "tlbrIconzList" to decide what function 
   has to be called. The decision is made primarily in
   processToolbarFunctions().

   The buttons can have left and right click actions associated.
   Some of them invoke CreateSoloSliderWidgetWin(), eg.,
   tlbrFloodFillSlidersInvoker(). These are pop-up sliders. Others
   allow users to click and drag to adjust a value, eg.,
   tlbrChangeStuffRotation().


h) Input responses
=====================================================================

   All keyboard shortcuts are «registered» through WM_KEYDOWN and
   WM_SYSKEYDOWN. initInterfaceModule() registers these Window
   Messages to dispatchKeyDown(), which passes them on based on the
   window that receives them: uiWM_KEYDOWN() handles the main window
   and the viewport, while WM_KEYDOWN() handles all the other windows,
   eg. the panels and the toolbar. Both functions are meant to
   finish execution as soon as possible. constructKbdKey() is called to
   convert the virtual keys into a readable form. uiWM_KEYDOWN()
   opens the menu bar on Alt+letter and passes the other keys to
   ProcessCriticalKeys(), which acts at once on the keys that cannot
   wait, eg. Escape or the keys that stop a slideshow. The remaining
   keys reach KeyboardResponder() through PreProcessKbdKey(), which
   both handlers run from a short timer. KeyboardResponder()
   is where each keyboard shortcut is actually registered,
   where the code decides what functions to call based on the keyboard
   input, and the user context, in-app conditions. QPV allows
   custom-defined keyboard shortcuts. These are stored as an object:
   "userCustomKeysDefined". The object is initialized by
   loadCustomUserKbds(). In KeyboardResponder(), if the user-pressed
   key is not customized [or defined] in the aforementioned object,
   the key is passed to processDefaultKbdCombos().

   Users can define custom keyboard shortcuts through
   PanelQuickSearchMenuOptions(), by right-clicking on any item found
   in the search results list. PanelDefineKbdShortcut() is the panel
   that allows users to define the new keyboard shortcut,
   via BtnApplyNewKbdShortcut().

   The mouse clicks on the main window and the viewport are
   handled in "module-interface.ahk": uiWM_LBUTTONDOWN(),
   WM_LBUTTON_DBL() and WM_MBUTTONDOWN() invoke WinClickAction(),
   found in the main file. The function handles most of the envisaged
   responses to mouse clicks, based on user context. Several
   examples:
     - thumbsListClickResponder()
     - ActPaintBrushNow()
     - ActDrawAlphaMaskBrushNow()
     - PerformVectorShapeActions()
     - updateTinyPreviewArea()
     ... and many more: WinClickAction() has over 700 lines...

   The WM_MOUSEMOVE message is registered to dispatchMouseMove().
   On the main window and the viewport, uiWM_MOUSEMOVE() changes
   the mouse cursor to different states, based on the user context,
   and queues MouseMoveResponder() with QPV_post(); the latter
   handles live viewport updates related to hover actions.

   On the other windows, WM_MOUSEMOVE() handles the message. Most
   importantly, it displays tooltips when users hover over icons in
   the QPV toolbar, if it is visible. The toolbar is created by
   createGUItoolbar(), if "ShowAdvToolbar" equals 1.


i) Image live editing
=====================================================================

   The tool panels are created using createSettingsGUI() with the
   parameter "isImgLiveEditor" set to 1. If the panel does indeed open,
   then the "imgEditPanelOpened" global variable is set to 1. These can be
   invoked by keyboard shortcuts, menus or via the toolbar.

   When a live editor panel is opened, it can be collapsed into a small
   widget. The widget is created with CreateCollapsedPanelWidget(). The 
   viewport is also responsive to clicks and keyboard actions specific
   to this mode. The toolbar is also updated with specific icons, based
   on the active tool, via createGUItoolbar() and CoreGUItoolbar(). 

   Such panels have their controls attached via g-labels to a
   function prefixed with "updateUI*", eg. updateUIfillPanel(). Such
   functions update the status of the different available controls: they hide,
   show, disable or enable controls.

   The Apply button in these panels is usually attached to
   applyIMGeditFunction(). The function is just a wrapper which invokes 
   a specific function for each tool, eg. BtnDrawShapeSelectedArea(),
   based on the "AnyWindowOpen" value. Most of these functions are named
   with this pattern: "Btn*SelectedArea". These functions invoke the
   actual functions that output the final result, on the image itself.

   The live preview in the viewport is handled by
   corelivePreviewsImageEditing(). This is another wrapper that handles 
   how the live preview is drawn on screen and other things. It invokes 
   a specific function for each tool, eg. livePreviewInsertTextinArea(),
   based on the "AnyWindowOpen" value. Most live preview functions 
   that render the preview on screen have this prefix: "livePreview*".

   Dedicated efforts have been put into generating live previews that do
   not exceed the viewport area, to keep the performance acceptable 
   while staying as faithful as possible to the final output users 
   get when they press Apply. Many 
   functions cache generated bitmaps to avoid re-rendering everything, 
   e.g., generateAlphaMaskBitmap() will reuse the cached bitmap when the
   preview relies on the same alpha mask options.

   When viewport colour adjustments are active, 
   mergeViewPortEffectsImgEditing() is called first, before the actual 
   function of the tool that applies the modifications to the main bitmap.

   Flood fill and the brush tool, though labelled as live tools, do 
   not have live preview functions. The actions are live themselves.
   The functions are: ActFloodFillNow() and ActPaintBrushNow().

   Some tools allow users to paint in the alpha mask, eg., fill selected
   area. When the user activates this option, toggleAlphaPaintingMode()
   is called. The live brush response during painting is handled by
   ActDrawAlphaMaskBrushNow() together with the specific live preview
   function of the active tool. In this mode, one undo level is recorded.

   When drawing tools are used, "liveDrawingBrushTool" is set to 1.

   The aforementioned functions, ActDrawAlphaMaskBrushNow(), ActFloodFillNow()
   and ActPaintBrushNow() are invoked by WinClickAction() when users click 
   on the canvas.

   When images are edited, two images are continually updated:
   "UserMemBMP" and gdiBitmap. "gdiBitmap" is used for the viewport.
   "UserMemBMP" is the edited bitmap.

   When editing images under 536 megapixels, 100 levels are recorded,
   via wrapRecordUndoLevelNow(). Otherwise, one undo level is recorded 
   by recordUndoLevelHugeImagesNow(). The undo/redo actions are handled 
   by ImgUndoAction() and ImgRedoAction(). The array "undoLevelsArray"
   holds the IDs of the different undo states and GDI+ bitmaps.

   When editing images above 536 megapixels, the image data is handled 
   through FreeImage and most of the tools have counterparts that work
   on the FreeImage bitmap. "UserMemBMP" and "gdiBitmap" are not used.
   The array "undoLevelsArray" is also not used with such large bitmaps.
   The image data is accessible via the "viewportQPVimage.imgHandle"
   property and the methods of the "screenQPVimage" class. The image editing
   functions that rely on FreeImage, for very large images, begin with
   the prefix "HugeImages*".

   For images under 536 megapixels, the entire image is recorded for
   every undo level and is always 32-bit RGBA. But for bigger images,
   only a subsection of the image is recorded, when possible, and it can
   be at a colour depth of 24 or 32 bits.

   Many of the image editing tools rely on C++ functions invoked via
   DLL calls from "qpvmain.dll" written by me.

   Garbage collection is mainly performed via resetMainWin2Welcome().
   In this function, various objects are discarded, including viewport 
   image caches and image undo levels.


j) How to enable alpha masking for an image editing live tool
=====================================================================

   1. Add the window ID to isAlphaMaskWindow().
      The window ID is "AnyWindowOpen". The panels are created using
      createSettingsGUI().
 
   2. Add uiADDalphaMaskTabs(tab-ID-A, tab-ID-B, funcUIpanel) in the
   function creating the panel of the tool, eg.,
   PanelFillSelectedArea(). This will add the specific alpha masking
   options/controls in the panel.
      tab-ID-A and B are the tab order in the panel created.
      "funcUIpanel" is the reference to the function of the panel
      used to update the user interface elements and the viewport,
      eg., updateUIfillPanel().
 
   3. In UItriggerBrushUpdate(), add a pointer to "funcUIpanel"(),
   as explained previously, based on the "AnyWindowOpen" value.
   Do the same in BtnToggleBrushColors().
 
   4. In "funcUIpanel"(), add calls to updateUIalphaMaskStuff(1) and 
   updateUIalphaMaskStuff(2) based on the "CurrentPanelTab". This
   makes the alpha mask controls show or hide
   as users expect.
 
   5. Define the "viewportDynamicOBJcoords" object properties: x, y,
   w, h and zl. It must be defined inside the live preview drawing
   function of the tool itself, eg., livePreviewSimpleColorsAdjustImage(),
   which livePreviewAdjustColorsArea() calls.
   The object is used by MouseMoveResponder().
 
   6. The live preview drawing function must generate a bitmap and
   then pass it to realtimePasteInPlaceAlphaMasker() based on
   decideAlphaMaskingFeaseable(). See livePreviewSimpleColorsAdjustImage()
   as an example. Alternatively, when alpha mask painting mode is
   activated, for performance considerations, a direct call to
   QPV_MergeBitmapsWithMask() is suggested, as in
   livePreviewSimpleColorsAdjustImage().
 
   7. Update toggleAlphaPaintingMode(), the commented section «tools
   with no object as reference», and «create new bitmap for these
   tools». Add the AnyWindowOpen ID of the tool to the isVarEqualTo()
   if condition. The user alpha mask bitmap must be created based on
   the selection area dimensions.


k) Vector shapes drawing mode
=====================================================================

   When users start drawing a vector shape, startDrawingShape() is 
   invoked. The function prepares a bunch of things. The global 
   variable named "drawingShapeNow" is set to 1. If the selection
   area has a vector shape already defined, resumeCustomShapeSelection()
   is invoked to convert the points data to the edit mode data.

   At every mouse move, drawLiveCreateCustomShape() is invoked by 
   additionalHUDelements() to refresh the window. The function
   caches the points data. When the data is cached, it is rendered
   by drawVisibleVectorPoints() invoked from drawLiveCreateCustomShape(). 

   When the user clicks in the viewport, WinClickAction() invokes 
   PerformVectorShapeActions(). It can add, move or delete points. This
   function is also called by some context menu options listed by
   createContextMenuCustomShapeDrawing().

   When the user exits the tool, stopDrawingShape() is called.
   This function converts and saves the points data for later use.

   Users can load and save vector shapes through PanelManageVectorShapes().

   Undo levels in the vector editor mode are handled by
   recordVectorUndoLevels() and restoreGivenVectorUndoLevel().

   \\Technicalities:
   
   The points are stored in an array object:
   customShapePoints[index] := [x, y]

   The data is held in pixel units while the user edits the shape, but
   outside the edit mode, the values are relative to a bounding box
   with values from 0 to 1. In both cases, X and Y are floating-point numbers.

   "prevDestPosX" and "prevDestPosY" define where the image was last
   painted in the viewport. It is the top/left anchor point of the image.

   Please see getVectorCoordsFromVPpoint() and getVPcoordsVectorPoint()
   to find out the exact formulas.

   Outside edit mode:
   The vector points are used to calculate the coordinates of the points
   for GDI+, based on the width and height of the viewport selection area
   bounding box. One of the relevant functions is 
   convertCustomShape2givenArea() called by createImgSelPath().

   The points are stored in the same format when a user chooses to save
   a vector shape to disk via saveCurrentVectorShape().


l) List view and thumbnails list (soon)
=====================================================================

   QPV_ListViewGridHUDoverlay()
   QPV_listThumbnailsGridMode()
   QPV_ShowThumbnails()

   Thumbnails are generated by a pool of worker threads living inside qpvmain.dll;
   see thumbs-pool.h and freeimage-dynamic.h in the DLL sources.

   initThumbsPool()         starts the workers once per process
   QPV_ThumbsPoolBegin()    configures them for one QPV_ShowThumbnails() run
   QPV_ThumbsPoolSubmit()   queues one image [kind 0] or one cached thumbnail [kind 1]
   QPV_ThumbsPoolReady()    NumGet() on the shared status block; no DllCall to poll
   QPV_ThumbsPoolDrain()    collects finished GDI+ bitmaps; ownership moves to AHK
   QPV_ThumbsPoolEnd()      cancels the leftovers of a run
   QPV_ThumbsPoolShutdown() joins the workers; called from TrueCleanup()

   What actually runs in parallel, and what does not. WIC has no global engine lock, so the image
   decoding and the Fant scaling run concurrently, one decoder chain per worker; a single
   image is still decoded by one thread. FreeImage is likewise safe for distinct FIBITMAPs.
   GDI+ does hold process-wide locks. SVG rendering uses a Direct2D factory per worker,
   created SINGLE_THREADED on first use, because the shared pD2D1Factory is MULTI_THREADED
   and that flag means "locked", not "parallel". PDFium has global state and no thread
   safety at all; it stays serialized behind tpPdfMutex, so PDF thumbnails are built
   one at a time.

   Both pools try the loaders in one order: SVG and PDF to their own renderers,
   then FreeImage for the extensions it claims [RegExFIMformPtrn], then WIC for the ones
   it declares [RegExWICfmtPtrn, minus svg and pdf], then GDI+ [tpGDIPload()] for what is
   left over - EMF, WMF and the GIFs FreeImage refuses and WIC cannot decode, which is
   what LoadFileWithGDIp() ends up drawing in the viewport - and for anything the loader
   that did claim the file failed to open. That last one inherits the process-wide GDI+
   locks, so a folder full of them decodes with far less overlap than a folder of JPEGs;
   it is also the loader that hands back a copy and disposes the file-backed bitmap,
   because GDI+ keeps the file mapped until it goes.

   The drawing loop of QPV_ShowThumbnails() waits on the workers instead of doing the
   decoding itself, so it needs its own ways out: it stops when everything is painted,
   when the user aborts or scrolls, when the workers report nothing pending while some
   images are still expected, and when nothing at all was delivered for 69.5 seconds
   [lastPoolProgress]. That last one covers a decoder that never returns. For the same
   reason thumbsPoolShutdown() waits at most 5 seconds for the workers to report
   themselves out and abandons the ones that did not, rather than blocking app exit.

n) How to add a new panel/tool
=====================================================================

   Assign a unique window ID to the new panel (e.g., IDwin := 99). This value
   represents the active panel ID and is assigned to the "AnyWindowOpen" variable.
   The IDs are allocated by hand and there is no central table of them. You can
   do a grep for createSettingsGUI( and fakeWinCreator( to find one that is
   still free.

   Live image editing tools belong in BTNopenPrevPanel(). Add the panel ID there 
   to have your panel tracked. If an ordinary panel needs a "Back" button to the
   panel that invoked it, call getHostPanelFunc() before createSettingsGUI().
   See BtnCollectFileInfos() and PanelCachesOverview() for the pattern.

   Create the panel function, such as PanelMyNewTool(). Inside this function you must
   call createSettingsGUI(IDwin, A_ThisFunc) to initialize UI font configurations.

   Add the user interface elements inside the AHK GUI named "SettingsGUIA". You can
   add custom controls I created by calling functions such as GuiAddEdit(), 
   GuiAddDropDownList(), GuiAddCheckBox(), GuiAddButton() or GuiAddSlider().
   At the end of the PanelMyNewTool() function, to centre and display the window,
   invoke repositionWindowCenter("SettingsGUIA", hSetWinGui, PVhwnd, "Panel title").
   "hSetWinGui" is a global variable, the handle of the panel window.
   Read g) for more details regarding windows and GUIs.

   Each interactive control should have a gLabel associated with one function
   (e.g., updateUIMyNewTool() ) that handles toggling controls based on user 
   interactions. The same function should also invoke viewport updates if it is a live
   image editing tool. In the main AHK file, there are several updateUI*() functions 
   you can look at.

   If the panel is a live image editing tool, it must be registered as such, when invoking
   createSettingsGUI(), by passing 1 to the "isImgLiveEditor" function parameter. You
   should also create a new function, such as livePreviewMyNewTool() and register it in 
   corelivePreviewsImageEditing() based on the value of "AnyWindowOpen" associated with 
   the newly created panel. If alpha masking is to be supported, add the same ID to
   isAlphaMaskWindow() and in PanelMyNewTool() invoke uiADDalphaMaskTabs() to add 
   the panel alpha masking settings.

   The image data processing should happen in C/C++ functions, inside qpvmain.dll,
   or via GDI+. Most of the image editing tools in Quick Picto Viewer rely on the DLL.

   The image processing function meant to be executed on Apply should be registered
   in applyIMGeditFunction().

   To store settings, create corresponding functions: ReadSettingsMyNewToolPanel()
   and WriteSettingsMyNewToolPanel(). It is recommended to store the data in the
   registry for settings that do not pertain to the image viewer functions.
   Call RegAction() or IniAction() for each global variable to store or load it.

   You can register a keyboard shortcut for the panel in processDefaultKbdCombos().
   You can add a menu item to open the panel in one of the many functions that begin
   with createMenu*(). Use the kMenu() helper function to have it automatically indexed
   by the search menu options panel.

   The function that actually processes and outputs the pixels, invoked on Apply,
   should end by calling wrapRecordUndoLevelNow(newBitmap) with the resulting
   GDI+ bitmap. This is what commits "newBitmap" as the current "gdiBitmap" /
   "UserMemBMP" and records the undo level. Forgetting this call means
   the edit is neither applied nor undoable. When editing images above 536
   megapixels, call recordUndoLevelHugeImagesNow() instead, from your HugeImages*
   counterpart function, following the pattern used by the other tools.

   If your tool is meant to work directly on images above the 536 megapixels GDI+
   limit [ie. you implemented a HugeImages* counterpart, see section i)], its window
   ID must also be added to the isVarEqualTo() check found near the beginning of
   createSettingsGUI(), right before the call to downscaleHugeImagesForEditing().
   If you skip this, opening your panel while such a huge image is loaded will make
   QPV offer to downscale it first [or refuse outright], instead of letting your
   tool operate on it directly.

   If your live preview function caches bitmaps in Static variables, to avoid
   regenerating the same preview repeatedly (a common pattern; see
   livePreviewSymmetricaImgArea() for reference), it should support a "kill" mode
   that disposes of any cached bitmaps. Add a call to your live preview function
   with "kill" as the parameter, inside CloseWindow(), in the section handling
   imgEditPanelOpened=1, next to the existing ones, eg.,
   livePreviewInsertTextinArea("kill") and corePasteInPlaceActNow("kill"). Otherwise,
   the cached bitmaps linger in memory. 

   If your tool relies on custom mouse interactions instead, eg., picking a colour
   or a texture source point, or painting with a brush, add a branch keyed on the
   "AnyWindowOpen" value inside WinClickAction(). See ActFloodFillNow(),
   ActPaintBrushNow() and the AnyWindowOpen=64 / AnyWindowOpen=81 branches
   in there, as examples.

   Optionally, to give the panel its own toolbar launcher icon, register it inside
   CoreGUItoolbar(): add another button to the list of static objects named BTN*
   and to the "btnzList" string. In CoreGUItoolbar() add a call to tlbrAddNewIcon()
   with the newly defined static button object, then wire its click behaviour in
   processToolbarFunctions(). See section g) for more details on the toolbar internals.

p) AHK_H remnants [before v6.3.5]
=====================================================================

   Up to v6.3.00, QPV ran on AutoHotkey_H [AHK_H], a fork of AHK v1.1
   that can run several scripts as threads of one process. The user
   interface lived in its own thread, built from module-interface.ahk;
   the thumbnails, too, were made by such threads until v6.3.00, when
   the worker pool of qpvmain.dll replaced them. In v6.3.5, I eliminated
   AHK_H: QPV runs on the standard AHK v1.1 and the main file includes
   module-interface.ahk like any other library. Remnants of the
   two-thread design can still be identified:
     - seven functions of module-interface.ahk carry a "ui" prefix,
       because the main file has one of the same name: uiWM_KEYDOWN(),
