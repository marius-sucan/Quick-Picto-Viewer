# QPV bug audit — 2026-08-26

Whole-codebase audit run 2026-08-26 on master @9cb0419 (AHK sources + `QPV DLL source code/`).
Reported to the user; **not fixed at the time of writing**. Line numbers are as of 9cb0419.
Everything below was traced in the code; nothing could be executed on this machine, so the
reproduction steps describe what the code does, not what was observed on screen.

## Confirmed, most severe first

1. **"Load it partially" mode for huge images renders nothing** —
   `lib/Class_screenQPVimage.ahk:49`, `:254` and `:267` still build their DllCalls from
   `whichMainDLL` (`DllCall(whichMainDLL "\WICgetRectImage", ...)`,
   `"\WICdestroyPreloadedImage"`, `"\WICpreLoadImage"`). `whichMainDLL` was a super-global holding
   `"qpvmain.dll"` until v6.1.60 (commit 563f1ca, 2025-02-12) removed it from the main file;
   nothing defines it any more, so the class calls `DllCall("\WICgetRectImage", ...)`. AHK_H's
   `GetDllProcAddress` (ahkdll `script2.cpp:13351`) splits at the last backslash, is left with an
   empty DLL name, `GetModuleHandle("")` / `LoadLibrary("")` fail, ErrorLevel becomes -3 and the
   call returns blank.
   Path: `LoadWICscreenImage()` :101601-101618 — an image beyond the GDI+ limits
   (`isImgSizeTooLarge()`: a side over 23160 px / over 536 MP, or over 715 MP) that WIC decodes is
   first handed to `teleportWICtoFIM()` :101636. When that returns 0 — the memory warning of
   `memoryUsageWarning()` :20959 answered with **"Load it partially"**, or a failed
   `FreeImage_Allocate` — the viewport object stays in WIC mode (`LoadImage(..., zx, 2)` :101604)
   and "very-large" is returned. Every paint then goes `retrieveQPVscreenImgSection()` :83240 →
   `ImageGetResizedRect()` → `WicGetRect()` → blank → `Return "error"` (:83370): nothing is drawn.
   The other readers of a huge image (:3793, :17394, :24694, :25108, :55384) get blank bitmaps
   too, and `DiscardImage()` cannot release the preloaded WIC bitmap (slot 12).
   Repro: with the quality warnings enabled, open a JPEG/PNG of more than ~715 megapixels whose
   decoded size is close to the physical RAM (so the "You are currently opening a very large
   image..." dialog appears) and click "Load it partially" — the dialog promises slow zoom/pan and
   no editing, but the viewport stays empty (or keeps the previous image) and nothing reacts to
   zoom or pan. Before v6.1.60 the same click displayed the image through the WIC rect reader.
   Fix: `"qpvmain.dll"` in the three places (or restore the global).

2. **Ctrl+S in thumbnails mode does not "Save files list now"** — `InvokeMenuBarList()`
   :66865 advertises `Save files list now  Ctrl+S` → `BTNsaveCurrentSlideshow()` :43873 (writes
   the .SLD/.SLDB in place), but the key dispatcher (`processDefaultKbdCombos()` :1201) maps `^s`
   to `PanelSaveImg()` :44934, which in thumbnails mode calls `PanelSaveSlideShowu()` :43776 — the
   "Save files list as" panel, the same one Ctrl+Shift+S opens (:38153 region: `+^s` →
   `PanelSaveSlideShowu`).
   Repro: open an .SLD list, press L for thumbnails, remove one entry (Alt+Delete) so the List
   menu shows "Save files list now  Ctrl+S"; press Ctrl+S → the Save-As panel opens instead of
   the list being saved; Ctrl+Shift+S opens the same panel. In viewer mode Ctrl+S is "Save image",
   as advertised.

3. **Seen-images "Days" chart never reports the days that lack data** —
   `PlotSeenDaysStatsNow()` :28932: `If (nYear . thisM>20200401)` compares the 6-digit YYYYMM
   against an 8-digit date, so it is never true and `dataSkipped` is never seeded for the calendar
   days missing from the list; the "N days lack data." note (:28981) never shows. The Months chart
   does it right (:28768 `nYear thisM>=202004`). Intended: `nYear thisM thisD>20200401`.
   Repro: seen-images statistics panel → Charts: "Months" reports "N months lack data." while
   "Days" (with gaps in the recorded days) never does.

4. **After pasting or importing files the image shown is the second-to-last entry** — seven
   sites set `currentFileIndex := (maxFilesIndex<2) ? maxFilesIndex : maxFilesIndex - 1`
   (`PasteHDropFiles()` :25320, :26964, `PasteFilesIntoGivenFolder()` :32134, the omnibox
   imports :42387/:42395, :64786, `GuiDroppedFiles()` :65031) and `DelayiedImageDisplay()` shows
   `IDshowImage(currentFileIndex)` with no offset.
   Repro: open a folder of 10 images, copy one image in Explorer, Ctrl+V in QPV → "Finished adding
   1 files..." but the image displayed is the folder's former last file, not the pasted one; same
   with drag & drop into the window. (Noted as an oddity in the 08-25 review; listed here because
   it is reproducible.)
