# Eliminate the ahk-h interfaceThread (module-interface.ahk)

## Context

QPV depends on AutoHotkey_H v1.1 solely to host `lib/module-interface.ahk` as a second in-process interpreter (`interfaceThread := ahkthread(...)`, quick-picto-viewer.ahk:456/458 — the comment at :460 states the intent: a responsive UI while main is busy). That thread owns the main window (PVhwnd), the four layered GDI view windows, the menu bar, tooltip/flyout/halo windows, live input capture (mouse, pen pressure, gestures, keyboard forwarding), the slideshow clock, the taskbar/DWM integration, and the app's exit state machine — while the main thread does all logic and all painting into those windows. Goal (user-confirmed): eliminate ahk-h entirely — merge the module into the main thread, switch to stock AutoHotkey v1.1 + official Ahk2Exe, and keep cancellation/abort working via pump-shims (no async-decode work in this plan; the dissociated-UI wish is consciously traded away).

**QPV = quick-picto-viewer.ahk (106,555 ln); MI = lib/module-interface.ahk (4,823 ln, ~1,350 of them `class taskbarInterface`).**

## Why merge — the answer to "are there other possible solutions?"

Plain AHK v1.1 has exactly one script thread; in-process GUI-on-a-second-thread is precisely the feature ahk-h added. Without ahk-h, "UI dissociated from the main thread" has only two shapes, and no third simpler trick exists:

1. **A second process** (plain-AHK interface exe; RPC over WM_COPYDATA/SendMessage or COM). Rejected: it preserves the polling architecture and requires a ~315-site transport rewrite, plus cross-process painting (main's `UpdateLayeredWindow` onto foreign-process hwnds is fragile; the clean fix is a shared-DIB present redesign), cross-process ownership/z-order/focus coordination, and crash/lifecycle management. The merge, by contrast, *deletes* 233 of those 315 sites outright (167 assigns + 66 reverse calls become plain globals/direct calls). The facade layer (Phase B) keeps this option swappable later at low cost if ever wanted.
2. **A C++ UI thread in qpvmain.dll.** Rebuilding chrome in Win32 is out of proportion; a narrow "input-mirror + present" variant dissolves once you notice async input reads + selective message pumping cover the paint-loop needs in-thread.

Everything else (ObjRegisterActive in-process, hidden-window RPC between pseudo-threads, v2 rewrite) is not parallelism or out of scope. **Decision: full merge.** Bonus: the merge removes 100% of the AHK_H dependency (verified — the 315 bridge sites + `ahkthread()` are the only H APIs in the repo) and structurally fixes existing bugs: the exit path's `Process, Close` fired ~10ms after `TrueCleanup` starts (racing the seen-images DB COMMIT, QPV:4457), the GUI-restart pref-blanking (restartEntireGui QPV:73224 passes 9 of 16 externObj fields), and the unwatched-thread-death failure mode.

## Verified architecture facts that shape the work

- **Painting is a non-issue**: one funnel, `doLayeredWinUpdate()` QPV:5826 (sole `UpdateLayeredWindow` at :5866), already main-thread. MI never paints.
- **Boundary is scalar-only**: main→iface 16 `ahkFunction` (only `BuildGUI`/`msgBoxWrapper` use returns), 45 `ahkPostFunction` (25 names), 167 `ahkassign` (41 mirrored globals), 14 `ahkgetvar` (9 vars); iface→main (`MainExe := AhkExported()`, MI:20) 40 posts + 15 gets + 11 assigns, all async. Sole pointer (`UserMemBMP` QPV:77325) is truthiness-tested only (MI:1889). Largest post = 4 args (H API caps at 10 string args — verified from the repo's ahk_h zip).
- **Liveness polls exist because paint loops hold `Critical, on` and never pump** (documented MI:69-73): `LbtnDwn` via `determineLClickState()` QPV:4298 (54 sites; already ORs `GetKeyState("LButton")` — cross-thread read is droppable); `penPressureRaw` via `getBrushPenPressure()` QPV:4306 (2 sites, inside the brush loops QPV:78621/79236; producer `WM_PENpressure` MI:1215 on WM_POINTER 0x0245-0x024A); abort flags set by iface input handlers and polled between work stages: `canCancelImageLoad` (QPV:74273/75731/75803/75828/75885), `alterFilesIndex` (QPV:85687), `colorPickerMustEnd` (QPV:48591), `animGIFplaying` (QPV:12370), and `determineTerminateOperation()` QPV:35425 which spin-waits while the iface thread shows the abort dialog (`askAboutStoppingOperations` MI:1034). One qpvmain.dll call in MI: `dupesEngineCancel` (MI:1030) = sqlite3_interrupt while main is inside `sqlite3_step`.
- **OnMessage string-mode REPLACES, never chains** (v1 legacy mode). 8 message numbers are registered on both sides (0x100/0x104/0x200/0x201/0x202 name/case-clashed diverged bodies; 0x203/0x20A/0x20E entirely different handlers — QPV:443-452 vs MI:57-98). Today's keyboard path itself relies on replacement semantics (MI:83-84 beep handlers on 0x100-0x108, then MI:86-87 re-registers 0x100/0x104). Unification is a hard prerequisite of the flip.
- **Collisions**: 37 function names in QPV∩MI (8 identical, 5 near-identical, 6 parallel-evolution, 18 different-job — e.g. `WinClickAction` 15-line iface dispatcher vs 645-line main body), +16 vs shell-stuff.ahk, +3 MDMF_* vs Gdip_All.ahk, +1 vs msgbox2.ahk (~57 total); 3 real SetTimer-name collisions (`mouseTurnOFFtooltip`, `updateUIctrl`, `PreProcessKbdKey`; `theSlideShowCore` main-side refs are commented); labels `GuiClose:/doCleanup:/mouseToolTipGuiaGuiClose/Escape`; GUI name `mouseToolTipGuia` used independently by both; **`PVmenu` is two different menus** (iface = menu bar MI:2240; main = context menu QPV:69085+); iface Gui numbers 1-5 vs main's 1,059 bare `Gui, Add` + ~22 bare `Gui, +Option` lines relying on named defaults.
- **Directive divergence is load-bearing**: main `DetectHiddenWindows On` (QPV:65) vs MI default Off — `identifyMenus()` (MI:2733) matches the *hidden* `#32768` window under DHW-On, which would turn the reader `#If` block's bare hotkeys (`RButton::`, `Left::`, `Space::`… MI:2740-2796) into system-wide key theft. **P0 fix.** Also `#IfTimeout` 35 vs 2000; `#Persistent` (MI only); the `detectToolbar` (MI:333) / `adjustCanvas2Toolbar` (QPV:97631) deliberate twins exist because of DHW.
- **Menus**: bar clicks post 23 dynamic `InvokeMenuBar*` names to main; main's builders (e.g. `InvokeMenuBarFile` QPV:66258) already JIT-rebuild dropdowns from current state, then block in `Menu, Show` (showThisMenu manubarMode=1, QPV:69939). The MSAA hover-switch/reader machinery (60ms timer MI:2415, F10 SendInput, 9-deep probe MI:2064, `constantMenuReader` MI:2860) exists because same-thread timers/hotkey subroutines don't run during the modal menu loop. MI:90-94 shows prior (commented) experiments with WM_MENUSELECT-style monitoring — the intended direction.
- **Exit path runs through MI**: `GuiClose` → `byeByeRoutine` MI:1808 (escalating veto machine reading 16 of the 41 mirrored globals) → posts `TrueCleanup` to main and hard-kills the PID via `TimerExit` MI:1910.

- **Post-merge freeze inventory** (accepted per user decision; pump-shims keep cancel working): #1 per-navigation sync decode (`LoadBitmapForScreen` QPV:75159; seconds for RAW/PDF/huge), #2 `GetFilesList` QPV:88151, #3 thumbs harvest spin (QPV:85750, `Critical` whole function), fades, filter applies, saves, dupes/batch stepping loops (cooperative — pumpable), `VACUUM` QPV:73626 + sqlite sorts (cancel restored in D3).
