# QPV bug audit — 2026-08-30 — `combineImagesMultiTiffGDIp()` / `combineImagesFimMultiPage()`

Targeted audit of the two "Join images into a single file" back-ends, run on master @db825f9
(the commit that added the GIF W/H option). Line numbers are as of db825f9. Their shared
helpers `coreImgCombinerLoadFimFile()` :62805, `combineImgsConvertDepth()` :62870 and
`BTNperformCombineIMGs()` :44022 are in scope, since that is where two of the defects live.

**Status: every finding below is FIXED in the working tree except #7 (settings persistence),
which the author chose to leave open.** See "Fixes applied" at the end for what changed and for
the three behaviour changes worth knowing about. Line numbers throughout are those of db825f9,
i.e. of the code as it was found.

Unlike the previous audits, the four FreeImage-level claims behind findings 1, 2 and 5 were
**executed, not reasoned about**: `libfreeimage 3.18.0` was unpacked from the Ubuntu package
and driven from a ~90-line C harness reproducing QPV's exact call order. The one AHK-level
claim that mattered (`NumPut` to a null address) was checked against the v1.1 C++ source and
**disproved** — see "Withdrawn" at the bottom. Caveat: QPV ships a *custom* r1909 FreeImage
build (`initFIMGmodule()` :99782 `srcDll`), so the harness proves stock behaviour; nothing in
the QPV changelog suggests the GIF plugin or `Rescale` were touched.

## A. `combineImagesFimMultiPage()` — the .gif path

### 1. "Set GIF dimensions (W x H)" produces **no file at all**, and still reports success

The option added in db825f9. `combineImgsConvertDepth()` :62873 colour-quantises every frame
to 8-bit palettised during phase 1, and then phase 2 :62656 rescales it:

```ahk
      If (setW>1 && setH>1 && setRes=1)
         hFIFimgX := trFreeImage_Rescale(imgList[i], setW, setH)
```

`trFreeImage_Rescale()` :15223 tries OpenCV first, but `OpenCV_FimResizeBitmap()` :15261
rejects exactly this input — `If (PixelFormat=1 && bpp<24 || ...) Return 0` — so it always
falls through to `FreeImage_Rescale()`, which converts palettised input to 24-bit before
resampling. The GIF encoder accepts 1/4/8 bpp only, so `FreeImage_AppendPage()` :62683
silently drops every page (it is `void` in FreeImage; the wrapper's return value is
meaningless), `header->changed` is never set, and because the multibitmap was opened with
`create_new=1` — which does not touch the file system until close — `FreeImage_CloseMultiBitmap()`
:62690 writes nothing and **returns TRUE**.

Measured (`FreeImage 3.18.0`, QPV's call order):

```
[B] FIF_GIF SupportsExportBPP: 1 4 8
[A] after ColorQuantize:  bpp=8  colortype=3 (FIC_PALETTE)
[A] after Rescale(32x24): bpp=24 colortype=2 (FIC_RGB)     <-- trFreeImage_Rescale fallback
[C] OpenMultiBitmap(create_new=TRUE): file exists right after open: no
[C] GetPageCount after 2 appends of >8bpp pages = 0
[C] CloseMultiBitmap -> 1        (success)
[C] file exists after close: NO -- nothing written
[ctl] same flow with 8-bit pages -> GetPageCount 2, file written, 5413 bytes
```

Repro: select 3+ JPEGs, List > Join images…, format `.gif`, tick "Set GIF dimensions (W x H)",
set e.g. 320 x 240, Join. QPV shows "Finished creating the multipaged image file: 3 pages" and
there is no file on disk.
Fix: re-quantise after the rescale — `imgList[i] := FreeImage_ColorQuantize(hFIFimgX)` when
`animus=1` — or rescale before `combineImgsConvertDepth()` runs in phase 1. Either way, check
`FreeImage_GetPageCount(multiFim)` before claiming success (see finding 3).

### 2. Frames that are already 8-bit are dropped from the GIF, because the **TIFF** depth setting leaks into the GIF path

`combineImgsConvertDepth()` :62870 is a single `If/Else If` chain over two unrelated axes:

```ahk
  If (imgBPPc!=8 && animus=1)          ; 62873  GIF: quantise
     hFIFimgC := FreeImage_ColorQuantize(k)
  Else If (imgBPPc!=32 && modus=1)     ; 62875  TIFF depth  <-- reached when animus=1 too
     hFIFimgC := FreeImage_ConvertTo(k, "32Bits")
  Else If (imgBPPc!=24 && modus=2)
  ...
```

When the input is *already* 8-bit the first test is false, so control falls into the TIFF
branches. `modus` is `userSaveBitsDepth` (:44053), i.e. the "TIFF maximum color depth"
dropdown, which `BtnChangeMultiPageFmt()` :43901 only **disables** for GIF — it keeps its
value, and `Gui, Submit` reads disabled controls. With it at 1 an 8-bit page becomes 32-bit
(harness: `ConvertTo32Bits(8-bit page): bpp=32`) and `AppendPage` drops it. Both call sites are
affected: :62556 for pages exploded out of a multi-page source, and :62858 for single-page files.

Which sources actually arrive as 8-bit is worth pinning down, because it is not the obvious set.
`coreImgCombinerLoadFimFile()` :62812 opens a GIF with `multiFlags := (GFT=25) ? 2 : 0`, and 2 is
`GIF_PLAYBACK`, under which FreeImage **composites** each page and `LockPage` hands back 32-bit
frames. Measured:

```
GIF, flags=2 (PLAYBACK)   page0=32bpp/colortype2   <-- QPV's GIF path
GIF, flags=0 (raw)        page0=8bpp/colortype3
8-bit TIFF, flags=0       page0=8bpp
```

So the pages of an animated GIF joined with «Join contained frames» **on** are 32-bit, take the
quantise branch, and survive. What does not survive is everything that reaches the function
already palettised: 8-bit PNG/BMP, single-frame GIFs and 8-bit pages of multi-page TIFFs — all of
which come through `FreeImage_Load()` :62884 or a `multiFlags=0` multibitmap. Note that fixing
finding 6 *widens* this set: with the checkbox off, every GIF is loaded by `FreeImage_Load()` at
`GIF_DEFAULT`, i.e. 8-bit. JPEGs are 24-bit and always worked; a mixed selection yields a GIF with
only the 24/32-bit frames in it (harness `[mix]`: 8-bit + 24-bit → page count 1 of 2, file written).

Precondition: `userSaveBitsDepth` must be 1, 2 or 3 when Join is pressed. A **fresh profile**
escapes, by accident: `PanelCombineImagesMultipage()` :43926 sets `userSaveBitsDepth := 5`, and
`RegAction(0, "userSaveBitsDepth",, 2, 1, 4)` :48351 turns that into the *default* for a missing
registry value, clamped to 4 — the one safe setting. Everything after that is on a knife edge:

- `GuiType::Submit` (AHK v1.1 `script_gui.cpp`) tests only `output_var && type != GUI_CONTROL_RADIO`
  — there is **no enabled or visible check** — so the disabled dropdown submits its index like any
  other control, and `BtnChangeMultiPageFmt()` :43885 runs `Gui, Submit, NoHide` *before* it
  disables anything, capturing whatever the user just picked.
- `WriteSettingsCombineIMGs()` :44045 is `ReadSettingsCombineIMGs(1)`, and `act=1` is the *write*
  branch of `INIaction()` :70719 (reached via `RegAction()` :70712) — it stores the live value
  rather than re-reading the clamped one.

So one visit to the depth dropdown is enough, and it also writes 1/2/3 to the registry, where it
stays for every later session. The affected population is "anyone who has ever touched that
dropdown", not "anyone who previously joined TIFFs".

Repro (works on the first try, fresh profile included): pick 2 **8-bit** PNGs, open the panel, set
format `.tiff` + "32 bits RGBA", set format back to `.gif`, Join. "Finished creating … N pages" and
no file. Two animated GIFs reproduce it only with «Join contained frames from selected files»
unticked — with it ticked their pages arrive composited at 32 bits and the join works.
Fix: guard the chain — `If (animus=1) { If (imgBPPc!=8) hFIFimgC := FreeImage_ColorQuantize(k)
Return … }` before the `modus` branches, so `modus` is only consulted for TIFF.

### 3. Every failure in phase 2 and 3 is reported as success

Nothing downstream of the append loop is checked, and the one value that would expose findings
1 and 2 is computed and thrown away:

- :62629 `multiFim := FreeImage_OpenMultiBitmap(file2save, formatu, 1, 0)` — return unchecked.
  It fails when the `FileDelete` at :62624 failed (read-only file, file open elsewhere), when
  the folder is not writable, and for **any destination path outside the system ANSI codepage**:
  the wrapper marshals it as `"AStr"` (`lib/freeimage-wrapper.ahk:820`) because FreeImage has no
  Unicode `OpenMultiBitmap`. The .tiff sibling uses `"WStr"` via `GdipSaveImageToFile`, so
  `D:\Фото\out.tiff` works and `D:\Фото\out.gif` does not.
- :62683 `FreeImage_AppendPage(...)` — FreeImage returns `void`; the wrapper's `DllCall` has no
  return type and reads whatever is in the return register. Unusable and unused.
- :62687 `z := FreeImage_GetPageCount(multiFim)` — **the correct answer, discarded.**
- :62690 `r := FreeImage_CloseMultiBitmap(multiFim, 0)` — discarded.
- :62643 an abort inside the phase-2 loop sets `abandonAll := 1` and breaks, and then
  **nothing reads it**: the multibitmap is still closed and saved, and :62700 reports all
  `tFrames` pages as written. Phase 1's abort (:62526) is handled properly, and the .tiff
  sibling deletes its partial file (:62475); this path does neither.
- :62700 the success tooltip is unconditional.

Repro: any of findings 1, 2 or 4 above; or press Escape during "Phase 2" and confirm.
Fix: bail out on a null `multiFim`; compare `FreeImage_GetPageCount(multiFim)` against `tFrames`
before the final tooltip and report the shortfall the way the .tiff path reports `failedFiles`;
honour `abandonAll` after the loop.

### 4. The destination file is deleted with no confirmation

```ahk
   If FileExist(file2save)          ; 62623
   {
      FileDelete, % file2save
      Sleep, 100
   }
```

The save dialog is opened without `OFN_OVERWRITEPROMPT`: `BTNperformCombineIMGs()` :44032 passes
`optionz := "PathMustExist"`, `openFileDialogWrapper()` :34442 appends only
`" NoChangeDir HideReadOnly"`, and `Dlg_OpenSaveFile()` (`lib/shell-stuff.ahk:547`) builds the
flags from exactly that text. So no prompt comes from Windows either. Both siblings ask first —
`combineImagesMultiTiffGDIp()` :62277 and `CombineImgsIntoPDF()` :44094 — and both ask *before*
doing any work; this one deletes after phase 1 has already run, when the user can no longer
back out. `FileDelete`'s failure is unchecked, which then feeds finding 3.

Repro: join images to a `.gif` name that already exists → the old file is gone with no question
asked, and (per findings 1/2) is often replaced by nothing.
Fix: move the .tiff function's confirmation block into `BTNperformCombineIMGs()` so all three
formats share it and it runs before phase 1.

### 5. The "clear any animation metadata" call does nothing

```ahk
      ; clear any animation metadata used by this dib as we'll adding our own ones
      g := FreeImage_SetMetadata(imgList[i], NULL, 9, NULL)   ; 62665
```

`NULL` is not defined anywhere in QPV (no `Global NULL`), so it is a blank local. The wrapper
(`lib/freeimage-wrapper.ahk:1024`) marshals the key as `"astr"`, and AHK's `DllCall` passes a
**pointer to an empty string**, never a null pointer — only `"Ptr", 0` would do that. FreeImage
deletes the whole metadata model only when `key == NULL`; with a non-null empty key it looks for
a tag named `""`, finds none, and returns TRUE. Measured:

```
[D] ANIMATION tags after seeding:                        1
[D] after SetMetadata(model, dib, "", NULL):             1   <-- QPV's call
[D] after SetMetadata(model, dib, NULL, NULL):           0   <-- intended
```

So the source frame's own animation model survives into the new GIF; only `FrameTime` is
overwritten (:62678). How much rides on that depends on which loader produced the page — measured
on the clone `coreImgCombinerLoadFimFile()` actually keeps:

```
PLAYBACK (GIF, checkbox on)  clone=32bpp  ANIMATION tags: FrameTime
FreeImage_Load / raw path    clone= 8bpp  ANIMATION tags: DisposalMethod FrameLeft FrameTime
                                                          FrameTop Interlaced NoLocalPalette
```

A composited PLAYBACK page carries only `FrameTime`, which is overwritten anyway — so with the
sub-frames checkbox on there is nothing to leak. The raw path is the live one: it keeps the
original canvas offsets and disposal, which is how a "joined" animation ends up with frames drawn
in the wrong place or not cleared between them. That path is taken for single-frame GIFs today,
and — once finding 6 is fixed — for **every** GIF whenever the checkbox is off.

Also masked by finding 2 until that is fixed: the pages that carry the full model are the 8-bit
ones, which were being dropped anyway.
Repro (after fixing 2 and 6): untick «Join contained frames», join two GIFs whose frames use
partial-frame optimisation.
Fix: pass a real null. The wrapper's key parameter is hard-typed `"astr"`, so it needs a branch —
`DllCall(..., "int", metaModel, "uptr", hImage, "uptr", 0, "uptr", fiTag)` when `key` is blank —
or a dedicated `FreeImage_ClearMetadataModel(hImage, metaModel)`. Passing `0` through the
existing signature does not help; `"astr"` marshals it as the string `"0"`.

### 6. "Join contained frames from selected files" is ignored for GIF

`userCombineSubFrames` is read in exactly two places: :62366 (the .tiff function) and :44162
(the extract-frames panel). `coreImgCombinerLoadFimFile()` :62812-62836 unconditionally opens
any GIF/TIFF source as a multibitmap and clones every page into `otherFrames`.
Repro: untick the checkbox, select 2 animated GIFs, format `.gif`, Join — you still get every
sub-frame, not two.
Fix: pass the flag into `coreImgCombinerLoadFimFile()` and skip the `tFrames>1` branch when it
is 0, the way :62366 does.

### 7. The GIF-specific panel settings are never persisted

`ReadSettingsCombineIMGs()` :48346 lists 12 variables; `userJoinIMGsW`, `userJoinIMGsH`,
`userJoinIMGres` (added at :391 in this commit) and `userCombineGIFframeDelay` are not among
them, although every other control on the panel is — a grep for each of the four across
`*.ahk` finds no `RegAction`/`INIaction` anywhere. All four reset to their globals on each
start: `0, 0, 0` and `100`.
Side effect of the `0` defaults: the two edits are built with `Gui, Add, UpDown, … Range2-32000`
(:43973, :43975), so the control clamps to **2** and a user who ticks the checkbox without typing
anything gets a 2x2-pixel GIF (see finding 1 for why they get nothing at all today).
Fix: add the four `RegAction()` lines; seed W/H from the first selected image's dimensions
instead of 0.

### 8. Latent: stale `z` reuse in the sub-frame loop

```ahk
               If (modus!=5 && animus=0 || animus=1)      ; 62555
                  z := combineImgsConvertDepth(otherFrames[A_Index], modus, animus)
               If z                                       ; 62558
```

`z` is a function-local that lives across iterations *and across outer files*, and is only
reassigned when the guard holds. If the guard ever goes false, `If z` sees the *previous* frame's
handle: the current frame is unloaded and lost, and the previous one is appended twice.

It cannot go false today, and neither half of it can: `(modus!=5 && animus=0) || animus=1`. The
sole caller (:44053) sits in `BTNperformCombineIMGs()`'s `Else ; used only for GIFs` arm, so
`animus` is always 1 — and it already was before db825f9 renamed the function. `modus=5` is
equally unreachable, because `RegAction(0, "userSaveBitsDepth",, 2, 1, 4)` :48351 clamps the
:43926 sentinel to 4 before the panel is even drawn. So the guard is a constant `true` and the
same guard at :62857 is too. Worth writing down because the code reads as though a TIFF caller
were still possible, and restoring one would land on this.
Fix: `z := ""` at the top of the loop body regardless; or drop the vestigial guard.

- Dead: `bonusList`/`bonux` :62632-62633 (never written, so the `bonux>0` unload at :62695 never

## B. `combineImagesMultiTiffGDIp()` — the .tiff path

Materially healthier than the GIF path: it confirms overwrites, deletes its partial file on
abort, and its `EncoderParameters` pointer arithmetic (:62418-62427) is byte-for-byte the same
as the reference `Gdip_SaveImagesInTIFF()` in `lib/Gdip_All.ahk:2315` and is correct.

### 10. Use-after-free of `multiBitmap` on both fatal-error paths

The tail at :62463-62468 runs unconditionally:

```ahk
   NumPut(EncoderValueFlush, NumGet(NumPut(4, NumPut(1, _p+0)+20, "UInt")), "UInt")
   _E := DllCall("gdiplus\GdipSaveAddImage", "UPtr", multiBitmap, "uint", _p)
   trGdip_DisposeImage(multiBitmap)
```

but both fatal branches inside the loop already disposed that bitmap — :62413 (`!nCount`) and
:62436 (`GdipSaveImageToFile` failed) call `trGdip_DisposeImage(thisBitmap)`, and `thisBitmap`
*is* `multiBitmap` (:62400). So GDI+ is handed a freed `GpImage*`. The reference function does
not dispose in either branch precisely so that its single tail dispose stays correct; the
disposes are a QPV addition.

The second `trGdip_DisposeImage(multiBitmap)` is harmless — :101824 checks `validBMP()`, and
:101838 zeroes the `createdGDIobjsArray` entry on the first dispose — but the raw `DllCall` at
:62464 has no such guard.

Repro: needs the TIFF encoder to fail, which is rare; the reachable variant is a destination on
a volume that fills up or goes away between the folder check and the write, giving a non-zero
`_E` at :62432.
Fix: drop the two `trGdip_DisposeImage(thisBitmap)` calls (matching the reference), or guard the
tail with `If (!fattalErr && _p)`.

### 11. The sub-frame reload is not validity-checked

```ahk
         If (A_Index>1)
         {
            thisBitmap := LoadBitmapFromFileu(imgPath, 0, 0, A_Index - 1)   ; 62371
```

The frame-0 load at :62359 is followed by `If !validBMP(thisBitmap)` :62360; this one is not.
An unreadable frame therefore still runs `selectedFiles++` :62390,
`Gdip_GetImagePixelFormat` / `Gdip_BitmapSetColorDepth` :62447-62449 and
`Gdip_SaveAddImage(multiBitmap, 0, _p)` :62452 on a null handle. Nothing crashes — GDI+ returns
`InvalidParameter` and `failedFiles++` fires — but `selectedFiles` counts *attempts*, not pages,
so the closing message at :62482 ("Images embedded: N") over-reports by exactly `failedFiles`,
and then lists the failures again as if they were on top of N.
Repro: tick "Join contained frames", select a truncated multi-page TIFF whose later pages do not
decode; the summary claims more embedded pages than the file has.
Fix: mirror the :62360 check; increment `selectedFiles` only after a successful add.

### 12. Aborting inside the frame loop leaks the bitmap just loaded

:62371-62377 — the reload happens, then `determineTerminateOperation()` sets `abandonAll := 1`
and breaks, with no `trGdip_DisposeImage(thisBitmap)`. One bitmap per abort; a large frame is a
few hundred MB.
Fix: dispose before the `Break`.

### 13. `_p` stays 0 if the encoder-parameter scan matches nothing

The `Loop, % nCount` at :62418 breaks on the first parameter with `NumberOfValues=1` and
`Type=EncoderParameterValueTypeLong`; if the installed TIFF encoder exposes none, `_p` stays 0.
`GdipSaveImageToFile(..., "uint", 0)` then writes an ordinary single-page TIFF, and every
subsequent `Gdip_SaveAddImage(multiBitmap, thisBitmap, 0)` returns `InvalidParameter`, so the run
ends with "Failed to embed <all but one> images". Degraded, reported, not silent — and **not** a
crash (see Withdrawn). Same shape exists in `Gdip_SaveImagesInTIFF()` :2379, worth fixing in both.
Fix: treat `!_p` after the scan as the same fatal error as `!nCount`.

### 14. Minor

- :62366 `totalFlames := mainLoadedIMGdetails.Frames + 1` — `.Frames` is a last-frame *index*
  everywhere except `LoadFileWithWIA()` :74833, which assigns `wiaImg.FrameCount`, a count. Via
  that loader `totalFlames` is one too many and the last frame is embedded twice — the exact
  problem `coreImgCombinerLoadFimFile()` :62827 documents having fixed on its own side. Only
  reachable when `allowWICloader!=1` and GDI+ has already failed, so narrow.
- Same line: if a loader ever reports 0 frames, `.Frames` is `-1` (`LoadFileWithGDIp()` :75113,
  `loadWICasFreeImage` path :101245 both do `count - 1`), `totalFlames` is 0, and `Loop, 0` skips
  the body entirely — the file is dropped without `failedFiles++` and its bitmap is leaked.
- :62391-62396 duplicates :62445-62450: the colour-depth conversion runs once before the
  `selectedFiles=1` test and again inside the `Else`. `Gdip_BitmapSetColorDepth()` converts in
  place, so the second call re-reads the format and no-ops — redundant, not wrong.
- Dead: `tFrames` :62310 (never read), `abandoned := 1` :62288 (followed immediately by `Return`).
- :62353 / :62385 — `countTFilez / filesElected` divides by zero if the selection vanished;
  per the verified AHK semantics that yields a blank progress fraction, not an error.

## Withdrawn during the audit

**"The unconditional `NumPut(…, _p+0)` tail at :62463 dereferences address 0 and crashes QPV
whenever the user aborts on the first file or every selected file fails to load."** False.
`BIF_NumPut` and `BIF_NumGet` (AutoHotkey v1.1 `source/script2.cpp:15733` and `:15472`) both
open with

```cpp
	if (target < 65536 // Basic sanity check to catch incoming raw addresses that are zero or blank.
		|| …)
	{ aResultToken.symbol = SYM_STRING; aResultToken.marker = _T(""); return; }
```

so the whole `NumPut(EncoderValueFlush, NumGet(NumPut(4, NumPut(1, 0)+20, "UInt")), "UInt")`
chain silently evaluates to blank, and the following `GdipSaveAddImage(0, 0)` just returns
`InvalidParameter`. The abort and all-files-failed paths are safe. This kills the crash claim
for finding 13 as well, and belongs with the other interpreter facts in
`ahk-runtime-semantics-verified`.

**"Disposing `multiBitmap` twice is a double free."** False — `trGdip_DisposeImage()` :101820
short-circuits on `validBMP()` and :101838 clears the tracking entry, so the second dispose is a
no-op. What survives is the raw `DllCall` in finding 10, which is not tracked.

## Verification harness

`QPV DLL source code/tests/freeimage_gif_oracle.cpp` — kept, but deliberately **not** wired into
`run-tests.sh`: it exercises the third-party FreeImage library rather than `qpvmain.dll`, and it
needs a FreeImage dev package the suite does not otherwise require. Its header carries the
build line (unpack `libfreeimage3` / `libfreeimage-dev` with `apt-get download` + `dpkg-deb -x`,
no root needed). It walks QPV's own order — `Allocate(24bpp)` -> `ColorQuantize` -> `Rescale` ->
`OpenMultiBitmap(GIF, create_new)` -> `AppendPage` x2 -> `GetPageCount` -> `CloseMultiBitmap` ->
`access()` — plus a control run with 8-bit pages, a mixed run, and the `SetMetadata` key
comparison. The same trick answers any future "which depths does this plugin accept / why did
the multipage save produce nothing" question, for WEBP and TIFF as much as GIF.

## Fixes applied — 2026-08-30, on top of db825f9

Three files: `quick-picto-viewer.ahk`, `lib/freeimage-wrapper.ahk`, `lib/Gdip_All.ahk`.
Findings 1-6 and 8-14 are fixed; **#7 was left open on request**.

**Two new helpers carry most of the GIF-side fix.**

- `combineImgsAddPage(k, modus, animus, setW, setH, setRes, imgList, ByRef tFrames, ByRef BMPmemSize)`
  is now the single path a page takes into `imgList`, for single-page and multi-page sources
  alike. It rescales **first** and converts depth **second** (#1), which also moves the resize
  ahead of the `BMPmemSize` accounting (#9) and retires the stale-`z` footgun by construction
  (#8). It owns `k`: whatever it does not store, it unloads.
- `askOverwriteDestFile(destFilePath)` asks once, deletes, and reports whether the caller must
  stop. Both `combineImagesMultiTiffGDIp()` and `combineImagesFimMultiPage()` call it before any
  work starts (#4). It also verifies the file is actually gone, rather than trusting `FileDelete`.
  `CombineImgsIntoPDF()` was deliberately left alone: its own prompt is interleaved with bitmap
  creation and it already asks.

**Per finding.**

1. Rescale moved into `combineImgsAddPage()` ahead of the quantisation. Verified end to end
   against real FreeImage 3.18 for six source depths x resize on/off — all now yield 8-bit pages,
   all pages land, and the files read back as valid 3-page GIF89a. Before: 0 pages, no file.
2. `combineImgsConvertDepth()` now branches on `animus` first, so the TIFF `modus` values can
   never touch a GIF page. An already-8-bit page is returned untouched; 1/4/16/48/64-bit pages
   get a 24-bit step before `FreeImage_ColorQuantize()`, which only accepts 24/32. This matters
   more after fix 6 than before it: unticking the checkbox routes every GIF through
   `FreeImage_Load()` at `GIF_DEFAULT`, i.e. 8-bit, rather than through `GIF_PLAYBACK`'s

3. `multiFim` is checked; `FreeImage_GetPageCount()` is read before the close and compared
   against `tFrames`, so a shortfall is named; `FreeImage_CloseMultiBitmap()`'s result and
   `FileExist()` gate the success message; the phase-2 `abandonAll` is honoured.
4. See `askOverwriteDestFile()` above. Both exporters also refuse an empty selection *before*
   touching the destination, so a stale selection can no longer destroy a file and then bail.

   Call site changed to `FreeImage_SetMetadata(imgList[i], 0, 9, "")`. Same note as above: this

**Three behaviour changes worth knowing about.**

- Aborting a `.gif` join during phase 2 now **deletes** the partial file instead of saving it,
  matching what the `.tiff` exporter has always done.
- A `.gif` join to an existing file now **asks first**, and asks before phase 1 rather than
  deleting after it.
- The `.tiff` abort beep changed from 900 Hz to 300 Hz, so both exporters use the same tone for
  an abort as the rest of the application.
